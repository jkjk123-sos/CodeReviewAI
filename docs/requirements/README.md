# CodeReviewAI 需求规格说明书（整合版）

本目录是小组需求的**统一入口**。五位成员各交一份分册，此处汇总为整合版 SRS。

## 一、为什么按人分文件，而不是合成一个大文件

五个人同时编辑同一个 `SRS.md`，每次合并都会在同一段产生冲突，且冲突内容往往是"两段都想保留"的表格行，手工解决极易丢内容。

因此约定：**每人一个文件，互不重叠；本 README 做索引与汇总**。合并时 Git 处理的是不同文件的增补，零冲突。

## 三、分册必须包含的六节

为保证五份合起来能读，每份统一六节结构：

1. **引言** —— 目的、范围（明确写"不在范围内"的部分）、术语
2. **总体描述** —— 本线在产品中的位置、上游输入、下游输出、约束
3. **功能需求** —— 表格：编号 / 需求 / 描述 / 优先级（MoSCoW）/ 验收判据
4. **非功能需求** —— 表格：编号 / 对象 / 指标（**必须带数字**）/ 测法 / 依据
5. **用例** —— 编号 / 用例 / 参与者 / 一句话 / 关系 / 对应需求
6. **追踪矩阵** —— 需求 → 用例 → 数据实体 → 制品 → 验证方式

## 五、提交与合并流程

```bash
# 1. 从最新 main 拉自己的分支
git checkout main
git pull
git checkout -b feat/srs-<线>

# 2. 只新增自己那一个文件，不要改动他人文件与 README
vim docs/requirements/srs-<线>-<姓名>-<学号>.md
git add docs/requirements/srs-<线>-<姓名>-<学号>.md
git commit -m "docs(srs): 提交 <线> 线需求分册"
git push -u origin feat/srs-<线>

# 3. 在 GitHub 上开 Pull Request，由组长合并
```

**为什么每人只改自己的文件**：合并时 Git 按文件比对，五人改五个文件，主线永远不会有冲突；README 的统计表由组长在合并后统一更新，避免五个人抢改同一张表。

## 六、整合版阅读顺序

1. 先读本 README 的第三节（六节结构）和第四节（统计），了解全貌
2. 再读 C 线分册，它是接口与契约的定义方，其余四线都依赖它的产物
3. 最后按 A → B → D → E 读，即可还原一条完整的审查链路：解析 → 判定 → 存储 → 验证
