## 1. 引言

### 1.1 目的

本册规定 C 线在 CodeReviewAI 中**对外提供什么、什么算做完、谁能验收**。C 线横跨 CLI 与 Web 两端，职责是把 A 线的解析结果、B 线的规则命中，装配成人能直接使用的产物：命令行报告、REST 接口、可读页面、CI 门禁判定。

因此本册定下来的内容以「契约」为主：命令行的参数与退出码、报告 JSON 的字段与校验、REST 接口的入出参、页面的三态与分页规则、CI 判定的分级口径。

### 1.2 范围

**在范围内：**

- 三个 CLI 子命令：`run` / `report` / `config`
- 报告契约：11 个字段 + 3 条一致性校验（V-01/V-02/V-03）
- 13 个 REST 接口 + 8 个错误码
- 列表页双分页（page / cursor）、详情页分组与定位、趋势页聚合
- CI 门禁：三档退出码、PR 评论汇总、失败注解

**不在范围内：**

- 源码解析与语法树（A 线）
- 规则库与分级策略的判定逻辑（B 线）
- 表结构的物理设计、索引与分区（D 线）
- 测试用例与 CI 脚本实现（E 线）
- AI 建议的生成（实验四，本册只定边界）

### 1.3 术语

| 术语 | 含义 |
|---|---|
| Finding | 一条命中：某文件某行触发了某条规则 |
| RuleHit | B 线输出的原始命中，C 线消费后装配成 Finding |
| DiffUnit | A 线输出的改动块，含文件路径与行号范围 |
| run_id | 一次审查的唯一标识（UUID） |
| 阻断（blocking） | 必须修复，CI 判失败 |
| partial | 审查未完整完成（如 AI 超时），结果不完整但可用 |

## 2. 总体描述

### 2.1 产品视角

CodeReviewAI 是一个本地优先的代码审查工具。开发者既能直接在终端跑一次审查，也能通过服务查看历史与趋势，还能在 CI 里用它挡住有阻断问题的提交。

C 线处在数据流的末端：上游给的是零碎信息，下游要的是成品。

```
A 线 DiffUnit ──┐
                ├──▶ C 线装配 ──▶ 报告（一份，三处消费）
B 线 RuleHit ───┘                 ├─ CLI 终端
                                  ├─ REST 接口 → 页面
                                  └─ CI 退出码
```

### 2.2 用户特征

| 用户 | 特征 | 关心什么 |
|---|---|---|
| 开发者 | 会用命令行，不读文档 | 快、输出能看懂、不打断心流 |
| 评审者 | 看 PR 评论 | 一条评论说清有几条阻断 |
| CI 机器人 | 只读退出码 | 0 / 1 / 2 三档稳定 |

### 2.3 约束

- 报告必须是**单一数据源**：CLI 与页面看到的数据来自同一份 JSON，不允许各自查询
- 退出码只有三档，不扩展
- 不引入 ORM（8 表 12 查询，抽象成本高于收益）
- 认证用 token，不做角色与登录

## 3. 功能需求

共 18 条，按 MoSCoW 排优先级：**M** 必须有、**S** 应该有、**C** 可以有。M 级 9 条、S 级 7 条、C 级 2 条。

| 编号 | 需求 | 描述 | 优先 | 验收判据 |
|:----:|------|------|:----:|---------|
| FR-C-01 | 跑一次审查 | `codereview run <path>` 或 `--diff <ref>`，出报告 | M | 给 3 个文件目录，10 秒内出报告 |
| FR-C-02 | 初始化配置 | `codereview init` 三问生成 `codereview.yaml` | S | 空目录跑一次，生成的配置能被 FR-C-01 读到 |
| FR-C-03 | 重看历史报告 | `codereview report <run_id>` 重渲染 | C | 新终端能读出昨天的报告 |
| FR-C-04 | 三种输出格式 | `--format text\|json\|sarif` | M | 三份输出对同一 diff 条数一致 |
| FR-C-05 | 退出码三档 | 0 无阻断 / 1 有阻断 / 2 执行失败 | M | 三种场景各跑一次，`$?` 分别是 0、1、2 |
| FR-C-06 | 配置三级合并 | 命令行 > 环境变量 > 配置文件 | S | 三处给不同值，生效的是命令行那个 |
| FR-C-07 | 触发审查接口 | `POST /api/v1/reviews`，返回 run_id | S | 返回 run_id，重复提交同 diff 不新建 |
| FR-C-08 | 列表分页筛选 | 分页、按等级/语言/时间筛 | M | 200 条数据，翻页稳定不重不漏 |
| FR-C-09 | 详情按规则分组 | 详情页按 `rule_kind` 分组，组内按文件排 | M | 274 条数据渲染成 8 组 |
| FR-C-10 | 规则清单接口 | `GET /api/v1/rules` 给规则号、名称、默认等级 | S | 返回 60 条以上，含中文名 |
| FR-C-11 | 趋势聚合接口 | `GET /api/v1/stats/trend` 按周聚合 | S | 给 8 周数据，返回 8 个点 |
| FR-C-12 | 列表页三态 | 有数据 / 空 / 出错，三种各有明确文案 | M | 三种状态各截一张图 |
| FR-C-13 | 详情页定位与色标 | 点条目跳到文件行，三等级三色 | M | 点第 37 行，定位到第 37 行 |
| FR-C-14 | 规则说明抽屉 | 点规则号弹出说明与示例 | C | 弹层能关，Esc 可关 |
| FR-C-15 | 趋势页 | 复用 D 线的图表组件，周维度 | S | 与 D 的组件视觉一致 |
| FR-C-16 | 键盘可达 | 列表→详情 12 次 Tab 内可达 | C | 不用鼠标走完全流程 |
| FR-C-17 | PR 评论汇总 | 一条评论内含分类计数与阻断清单 | M | 10 条阻断以内一条评论说完 |
| FR-C-18 | 门禁失败注解 | 输出 GitHub Actions 注解格式 | M | 失败时 PR 文件页能看到行内标注 |

### 3.1 报告契约（FR-C-04 的展开）

报告是一份 JSON，11 个字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `schema_version` | string | 固定 `"2.0"`，加字段靠它做兼容 |
| `run_id` | string | UUID |
| `repo` | string | 仓库标识 |
| `git_ref` | string | 分支或 `working-tree` |
| `commit_sha` | string | 40 位，本地跑时为全 0 |
| `status` | enum | `done` / `partial` / `failed` |
| `status_reason` | string? | `partial`/`failed` 时必填 |
| `counts` | object | `blocking` / `warning` / `info` / `total` |
| `kinds` | string[] | 本次出现的类别，去重 |
| `findings` | array | 每条含 `rule`/`rule_kind`/`level`/`file_path`/`line_start`/`message` |
| `duration_ms` | int | 耗时 |

**三条构造时强制生效的校验：**

| 编号 | 判据 | 拦住的问题 |
|---|---|---|
| V-01 | `blocking+warning+info == total`，且 `len(findings) == total` | 统计口径与明细不同源 |
| V-02 | `set(kinds)` 等于 `findings` 中 `rule_kind` 的去重集合 | 类别标签与实际命中不符，前端筛选会漏项 |
| V-03 | `partial`/`failed` 必须带 `status_reason` | 用户看到"部分完成"却不知原因 |

> 三条校验对应一次真实故障（评审记录 Q-05）：去重逻辑原写在子类，新加规则时漏写，导致 `total` 与 `findings` 条数不一致，报告构造失败。

## 4. 非功能需求

共 8 条，每条带数字与测法。

| 编号 | 对象 | 指标 | 测法 | 依据 |
|:----:|------|------|------|------|
| NFR-C-01 | 列表页首屏 | 200 条 ≤1.5 s（P95） | Chrome 冷缓存，Performance 面板取 20 次 P95 | 列表按仓库看，200 条是常见量 |
| NFR-C-02 | 单文件审查耗时 | 千行 ≤3 s（不含 LLM） | `time` 跑 1073 行样例，5 次取中位数 | 实测 ruff 0.281 s，留 10 倍余量 |
| NFR-C-03 | 首次可用 | ≤5 min | 从 clone 到出第一份报告，掐表 | 竞品零配置跑不起来，这是差异点 |
| NFR-C-04 | 镜像体积 | ≤300 MB | `docker image ls` | 审查工具不该比被审项目还大 |
| NFR-C-05 | 平台兼容 | Win10+ / macOS 13+ / Ubuntu 22.04 | 三平台各跑 `--version` 与一次审查 | 组内五人三个系统 |
| NFR-C-06 | 可定位 | 错误日志必含 run_id 与 trace_id | 故意造 3 个错误，看日志能否唯一定位 | 没有 trace_id 的错误等于没报 |
| NFR-C-07 | 中文完整 | 全中文、UTF-8，80 列不错乱 | Windows Terminal 80 列跑一次逐行看 | 组内终端宽度 80–200 |
| NFR-C-08 | 键盘可达 | 列表→详情 ≤12 次 Tab | 拔掉鼠标走完全流程 | WCAG 2.1 AA |
